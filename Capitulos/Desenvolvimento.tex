\chapter{Sistema Implementado}
\label{chap:sistema_implementado}

O TCC 1 definiu uma plataforma para reunir informações de amostras e análises do NAPI Abelhas. A implementação foi organizada em dois projetos: uma aplicação web e uma API. Este capítulo apresenta as funcionalidades identificadas nos projetos, as atividades de desenvolvimento e as alterações observadas em relação à proposta original.

\section{Requisitos e funcionalidades}
\label{sec:requisitos}

O fluxo implementado começa com os cadastros de apoio. A interface oferece telas para produtores e, na área administrativa, para cidades do IBGE, tipos de amostra, tipos de análise, espécies de abelhas, responsáveis e pontos de coleta. Cada ponto de coleta possui nome, cidade, latitude, longitude e raio opcional. O formulário administrativo utiliza um mapa para selecionar as coordenadas.

O registro de uma amostra exige nome, data de coleta e vínculos com um produtor, um ponto de coleta, uma espécie de abelha e um tipo de amostra. O identificador da amostra é gerado como UUID no banco de dados. Uma amostra pode possuir várias análises, cada uma vinculada a um tipo e a um responsável. O estado de uma análise pode ser \textit{pendente}, \textit{em preparo}, \textit{aguardando resultado}, \textit{em revisão}, \textit{concluída} ou \textit{rejeitada}. O esquema de dados não possui um estado próprio para a amostra.

Arquivos são representados pelos modelos \textit{FileGroup} e \textit{File}. A API fornece URLs temporárias para envio e leitura de objetos no MinIO. No frontend, o arquivo é transferido diretamente para o serviço de armazenamento, e a referência pode ser associada a uma análise. A implementação também admite um grupo de arquivos associado a uma amostra. O modelo não obriga a presença de imagens no cadastro inicial da amostra.

O acesso depende de uma sessão autenticada no Clerk. A aplicação utiliza uma organização ativa e distingue os papéis de administrador e membro. Na API, as rotas de escrita dos módulos de amostras, análises e cadastros exigem o papel de administrador; as consultas exigem autenticação e organização ativa. O identificador da organização é registrado nas entidades operacionais e empregado nas consultas desses módulos. Esse recorte de acesso amplia o perfil único de administrador previsto no TCC 1 \cite{clerk2026}.

\section{Atividades de desenvolvimento}
\label{sec:atividades}

As atividades observáveis nos artefatos do projeto podem ser agrupadas em quatro etapas, sem atribuir datas ou duração que não estejam comprovadas por registros de execução:
\begin{enumerate}
    \item \textbf{Modelagem e persistência:} definição das entidades e relações no esquema Prisma, incluindo o vínculo das entidades operacionais à organização e a separação entre metadados de arquivos e objetos armazenados.
    \item \textbf{API:} implementação de módulos NestJS para cadastros, amostras, análises e arquivos; validação de entradas com Zod; integração com Clerk e emissão de URLs assinadas para o MinIO.
    \item \textbf{Interface:} construção das páginas em Next.js para autenticação, navegação, cadastros, consulta de amostras, detalhe de análises e administração; inclusão do mapa de pontos de coleta.
    \item \textbf{Infraestrutura e verificação:} definição de serviços no Docker Compose, documentação da API com Swagger, rota de saúde que consulta o banco de dados e criação de testes unitários para componentes selecionados da API.
\end{enumerate}

Essas etapas substituem o cronograma prospectivo do TCC 1. A existência dos artefatos demonstra o trabalho de implementação correspondente, mas não comprova, por si só, implantação contínua, testes com usuários ou cumprimento dos prazos inicialmente previstos.

\section{Tecnologias e arquitetura}
\label{sec:arquitetura}

O frontend utiliza React com Next.js e o roteador baseado em arquivos do \textit{App Router} \cite{next2026}. A API foi construída em TypeScript com NestJS, sobre o adaptador Express, e expõe rotas HTTP sob o prefixo \texttt{/api/v1} \cite{nest2026}. Assim, a referência a Express no TCC 1 permanece válida como plataforma HTTP subjacente, mas NestJS é o framework que organiza os módulos, controladores e casos de uso.

O Clerk fornece autenticação e informações sobre a organização ativa. A interface envia o token nas chamadas à API; nela, guardas verificam a sessão, a organização e, nas operações restritas, o papel do usuário. O acesso ao banco de dados é feito pelo Prisma sobre PostgreSQL. Para arquivos, a API assina a operação e o navegador envia os bytes ao MinIO, evitando que a transferência do arquivo passe pela API. A Figura \ref{fig:arquitetura} representa esses componentes e fluxos.

O arquivo Docker Compose da API define serviços para a API, PostgreSQL, MinIO e Redis. A aplicação também registra um módulo de cache, porém não foi identificada uma conexão desse módulo a um armazenamento Redis nem uma política \textit{cache-first} aplicada às consultas. Por esse motivo, Redis é representado na figura como infraestrutura provisionada, e não como caminho de leitura comprovado. Não são apresentados indicadores de latência ou escalabilidade.

\section{Persistência de dados}
\label{sec:persistencia}

O esquema Prisma contém onze modelos: \textit{CidadesIBGE}, \textit{Produtor}, \textit{Responsavel}, \textit{TipoAmostra}, \textit{TipoAnalise}, \textit{Abelha}, \textit{PontoColeta}, \textit{Amostra}, \textit{Analise}, \textit{FileGroup} e \textit{File}. São sete cadastros de apoio, além das entidades de amostra, análise e arquivos. A Figura \ref{fig:der} resume as relações centrais e os campos relevantes ao fluxo estudado.

\begin{figure}[htbp]
    \centering
    \caption{Modelo de dados implementado: entidades e vínculos principais}
    \includegraphics[width=0.98\textwidth]{Imagens/diagramaDadosTCC2.png}
    \fonte{Autoria própria (2026), a partir do esquema Prisma da API.}
    \label{fig:der}
\end{figure}

\textit{Amostra} relaciona produtor, ponto de coleta, abelha e tipo de amostra. \textit{Analise} relaciona a amostra, o tipo de análise e o responsável, além de registrar seu estado. \textit{FileGroup} faz a associação opcional dos arquivos a uma amostra ou análise; \textit{File} guarda uma chave de objeto, seu tipo e metadados de envio. Os dados binários permanecem fora do banco relacional. A cidade é um cadastro de referência para produtores, responsáveis e pontos de coleta. O campo \texttt{orgId} representa a organização nas entidades operacionais, embora não exista uma tabela \textit{Organizacao} no esquema: o gerenciamento das organizações é delegado ao Clerk.

A presença de telas de busca não equivale à implementação do requisito de consulta filtrada: a interface envia parâmetros, mas a rota de listagem de amostras consulta os registros apenas pelo identificador da organização. Da mesma forma, os vínculos de origem registrados pela amostra representam rastreabilidade parcial, pois o local físico de guarda não faz parte do esquema. Essas diferenças orientam a apresentação dos resultados e dos trabalhos futuros.
